## 阻塞 1：设备端缺 5 个 macOS-SDK 工具

### 事实
1. 本机 Theos `/var/jb/var/mobile/theos` 只有 `iPhoneOS*.sdk`，**无 macOS SDK / 头文件** → 这 5 个工具
   （Makefile `TARGET := macosx:clang:latest:13.0`，链 AppKit / QuickLookThumbnailing）在设备上**编不了**。
2. 已用 GitHub `macos-14` 免费 runner（SDK `MacOSX14.5.sdk`，Xcode 15.4）编出 4 个并取回，**provenance 已锁定**
   （提交 `17df610c` / SDK 14.5 / thin **arm64e** / `platform=1(macOS) minos=13.0` / SHA-256 见 20_号文档）：
   - macwsdisplayd、macwsinputd、macwsinteropd、**macwsworkspacectl**（关键门禁工具）→ 已装入
     `/var/jb/usr/macOS/bin/` 与 chroot `/var/mnt/rootfs/usr/local/bin/`，双签 + 信任 CDHash。
3. `macwsneofetch` **未产出**（CI 那步对该工具构建失败被非致命跳过）。桌面核心不依赖它。
4. 装上后 `macos_gui.sh` 的"缺 workspacectl 就跳过"逻辑已自动失效，改为**真跑** `macwsworkspacectl`
   （`verify-launchservices-catalog` / `register-settings-extensions`）——但这两个动作目前**被 AMFI SIGKILL**（见阻塞2 交叉点）。

### 待补（可验证项）

  验证：在 Mac 上单独 `make -C macwsneofetch`，看编译/链接报错，补产物后加进 `dist/macws-tools/`。
- 【事实 A2】5 工具目前只"装进设备目录"，**未接入 `build_on_ios.sh` 的缓存校验**（类比 `MacWSWindowing` 的

## 阻塞 2：`dyld cache '(null)' not loaded: shared cache file is for a different platform`

### 事实
1. **能跑的**（thin、只依赖 cache 里少数库）：chroot 内 `sw_vers` → `macOS 13.4 / 22F66`，正常。
   `bash` / `plutil` / `cfprefsd`(root+501) 等此前也起来过。
2. **起不来的**（fat / ObjC 重依赖）：`launchservicesd`、以及依赖它的整条 lsd 链，dyld 报：
   ```
   dyld[xxxx]: dyld cache '(null)' not loaded: shared cache file is for a different platform
   Library not loaded: /usr/lib/libobjc.A.dylib
     Reason: tried:
       /System/iOSSupport/usr/lib/libobjc.A.dylib (no such file)
       /System/Volumes/Preboot/Cryptexes/OS/System/iOSSupport/usr/lib/libobjc.A.dylib (no such file)
       /System/iOSSupport/usr/lib/libobjc.A.dylib (no such file, no dyld cache)
       /usr/lib/libobjc.A.dylib (no such file)
       /System/Volumes/Preboot/Cryptexes/OS/usr/lib/libobjc.A.dylib (...)
       /usr/lib/libobjc.A.dylib (no such file, no dyld cache)
       /usr/local/lib/libobjc.A.dylib (...)
   ```
3. **缓存本身存在且是 macOS arm64e 缓存**：`/var/mnt/rootfs/System/Caches/dyld_shared_cache_arm64e[.01]`
   （cryptex 里同两份），文件头 identifier = `dyld_v1  arm64e`。CDHash `b5da3940…` / `bbb76598…`
   与 postinst 硬编码一致、已在 Dopamine trustcache。
4. **切片构成（otool 实测）**：`launchservicesd`、`sw_vers`、Dock、Finder 均为 fat
   = **x86_64 + arm64e**（**无纯 arm64 切片**）。两切片 `LC_BUILD_VERSION` 都是 `platform=1(macOS)`。
5. **dyld 是 macOS dyld**：`/var/mnt/rootfs/usr/lib/dyld` = `platform 1 / minos 13.4`。
6. **launchservicesd 当前是"50KB 薄加载器"**（`postinst` 用 `launchservicesd.macws-original`(951KB) 换的薄壳 +
   `launchservicesd.dylib` payload）。
7. `SharedCacheRuntime.cpp` / `preflightCacheFile()` / `validPlatform()` / `altPlatform` **不在本项目**
   （全工作区 grep 无命中，唯一命中是无关 iOS SDK 头）→ 这些是 **Apple dyld3 源码**里的函数；
   平台判定实际发生在**被补丁过的 `/var/mnt/rootfs/usr/lib/dyld`** 内部。

### 关键线索（据事实）
- 报错的搜索路径里出现了 **`/System/iOSSupport/...`**。`iOSSupport` 是 **macCatalyst / "macOS 上跑 iOS 运行时"**
  的目录。这说明**该 dyld 把 `libobjc` 解析路由到了 Catalyst/iOSSupport 前缀**，而不是普通 macOS
  `System/Library/...` 前缀 —— 即这个 dyld 的"平台/路径族"判定可能不在纯 macOS 语境。
  【假设 B1】：`launchservicesd` 走的 dyld 以 **macCatalyst 语义**解析系统库（前缀 `iOSSupport`），
  而它需要的是 **普通 macOS `dyld_shared_cache_arm64e`**；两者平台族不一致 → "different platform"。
  **验证**：在 Mac 上对该 dyld 反汇编/字符串，看它 open cache 时用的路径前缀与 `platform` 枚举，
  对比 `System/iOSSupport` 与 `System` 两套。

### 假设（均需验证，暂不断言）
- 【假设 B2】**内核 shared-region 层**：iOS 16.5.1 内核 chroot 里给 macOS 进程加载的是 **iOS 共享区**，
  而 macOS `dyld_shared_cache_arm64e` 的 CodeDirectory 平台是 macOS。即便文件都在、CDHash 都信任了，
  内核/dyld 因"运行时平台 != 缓存平台"拒载。
  **验证**：需一台 Mac 上 `lldb` 远程 attach 失败进程，读 `dyld` 里 `sharedCache.platform` 与
  进程 `validPlatform()` 的实参；或在 Mac 上 disassemble 该 dyld 的 cache-load 分支，看它比的是
  "header platform" 还是 "kernel-provided platform"。
- 【假设 B3】**16.5.1 组合本身不被 macOS-dyld 路径支持**（上游支持矩阵只有 iPad14,5/16.0 的 M2）。
  但按你的要求，**不下降级/套偏移/跳校验的结论**；只作为"若 B1/B2 都不成立则需上游确认"的备选。

### 我这边**做不了**、需要你补的（具体缺项）
1. **Apple dyld3 源码**（含 `SharedCacheRuntime.cpp` / `validPlatform()` / `altPlatform`）——仓库没有，
   需你本机那份，给我文件路径即可，我按你协议逐行对平台值。
2. **在 Mac 上反汇编/字符串该 dyld**：`otool -s __TEXT __cstring /var/mnt/rootfs/usr/lib/dyld`、
   以及 cache-load 分支。可把 `/var/mnt/rootfs/usr/lib/dyld` 拷到 Mac 我给你跑。
3. **内核 shared-region 观测**：需越狱侧 `sysctl` / `dtrace` 或 Mac 上 `lldb` 远程 attach（我这边只能到
   "dyld 拒绝"这一层，读不到内核把哪个 cache 映射进 chroot）。

## 交叉点（阻塞1 × 阻塞2）
装好 5 工具后，`macwsworkspacectl`（纯 macOS arm64e 平台工具）一进 chroot 也**被 AMFI SIGKILL**，
说明除了"缓存平台门槛"，**AMFI 对这些 fat/MacOS 二进制的代码签名校验**也在同时起作用
（薄加载器是 ad-hoc 签名 `launchservicesd.af633153.unsigned`）。这是两个独立墙：
- 墙 X（AMFI 签名/信任）：SIGKILL — 需要按项目"双签 + 信任终态 CDHash"规则补齐，且 5 工具/lsd 需正确平台签名。
- 墙 Y（dyld 缓存平台）：different platform — 见阻塞2，需 Mac + 源码定位。
**两者需同时解开才能点亮桌面**，不是只解 5 工具就够。

## 结论（严格）
- 阻塞1：**4/5 工具已编好装好（provenance 锁定）**；差 `macwsneofetch` 补编 + 接入缓存校验。
- 阻塞2：**平台不一致的来源尚未定位到行级**；已排除"缓存缺失/CDHash 未信任/放错位置"（都在、都信任、路径已硬链）。
  最可信的两个可验证方向是 **B1（dyld 按 iOSSupport/Catalyst 语义解析）** 与 **B2（内核 shared-region 平台）**。
  **在你提供 Apple dyld3 源码 + Mac 反汇编条件前，我不做"跳过校验/降级"的修复**，避免误伤。
